# M0b 探测报告

日期：2026-10-31。探测程序：`tools/M0bProbe`，最终版本 build 20261031135015。

报告只含统计数字。探测程序不保存屏幕文字、窗口标题或网址。

## 1. 结论

| 问题（PRD §16） | 结论 |
| --- | --- |
| 自签证书下授权是否保留？ | **保留。** 用固定证书「ThinkMyDay Local Signing」签名，指定要求（DR）是 identifier 加证书 leaf。前后重新构建并安装约 10 次，辅助功能和屏幕录制都不用重新授权。签名第一次使用钥匙串时，要点一次「始终允许」。 |
| 常用 App 能用辅助功能读到多少文字？ | **测到的 App 都能读到。** 修正可见性规则后，Claude、ChatGPT（Codex）、Chrome、Cursor 类编辑器、Koe 的「不可读」比例为 0–3%。和 OCR 对照，OCR 字数 ÷ AX 字数在 0.6–0.9 之间。 |
| Chrome 正文能否通过辅助功能读到？ | **能。** 不需要 `AXEnhancedUserInterface`（返回 -25208，不支持），正文本来就能读到。滚出视野的内容可以按坐标正确排除。 |
| Electron 是否需要 `AXManualAccessibility`？ | **需要。** Cursor 类编辑器（`com.anysphere.sand`）设置前读到 0 字，设置后中位 1,169 字。Claude 设置前后都能读到。这一步必须保留。 |
| 多窗口、多屏 | 第 1、2 段：97–100% 的采样同时有 2 个以上窗口，分布在 2 块屏幕上。第 4 段基本只有一个窗口。91–98% 能识别出焦点窗口。屏幕窗口和辅助功能窗口的匹配率为 78–100%（见 §4）。 |
| OCR | 能用，但正常情况下基本用不上（第 4 段半小时触发 2 次）。识别一个窗口：截图约 40–740 ms，识别 0.4–1.6 s，最慢约 7.2 s，有过 1 次超时。平均置信度只有 0.27–0.57。 |
| 资源占用 | 修复后 CPU 平均 0.5–1.3%，p95 0.6–4.0%，内存约 53–63 MB。Chrome 大页面最耗时，21% 的读取到了 400 ms 上限。 |
| 白天整理的用量 | **差别很大，取决于在做什么。** 用 AI 对话时每小时约 3.7 万 token，看网页时约 14 万 token。按 15 分钟一次，每次约 9 千–3.5 万 token。都是上限估计，见 §3.4。 |
| Chrome 历史库 | **读不到。** 系统拒绝访问 `~/Library/Application Support/Google/Chrome`，提示 “you don’t have permission to view it”。macOS 保护其他 App 的数据，需要「完全磁盘访问权限」。 |

## 3. 发现

### 3.1 Chromium 的可见性规则（对 M4 记录层最重要）

探测程序判断「哪些文字在屏幕上可见」，前后修了四次。每一处都是 Chromium 和 Electron 的特有行为，正式的记录层必须照着处理：

1. **`AXVisibleCharacterRange` 不可靠。** 普通文字（AXStaticText）几乎都报一个很短的范围，导致几千字被算成 1 字。现在只在可编辑控件（AXTextArea、AXTextField、AXComboBox）上用它裁剪长文本，其他元素按坐标判断。
2. **按钮、链接、标题的「标题」就是子元素的文字。** 两样都计入会重复计数。现在只在叶子元素上读标题。
3. **滚出视野的文字会被压成 1 pt 高的细条，贴在滚动区域边上，不会给出视野外的坐标。** Codex 里有 3,000 多字是这种情况。现在宽或高小于 2 pt 的元素算不可见。另外也按 AXScrollArea 和 AXWebArea 的边界裁剪。
4. **单行标签里藏着完整文本，屏幕上只显示一行加省略号。** 比如一个按钮带 612 字的预览，但只有一行宽。现在按框的大小估算容量上限：每字至少 6 pt，每行至少 14 pt。

修正后，第 3 段两次 OCR 对照的 OCR÷AX 为 0.86 和 0.58，第 4 段中位 0.85。AX 略多是正常的，因为 OCR 会漏掉小字、灰字和空格。

> 产品取舍：第 4 条只用于估算「屏幕上看得到多少」。**记录层保留被省略号截掉的全文**（Jonas 2026-10-31），发给模型前再按需要裁剪。

### 3.2 OCR 兜底

- 修复前，可见性 bug 让 OCR 兜底触发了 416 次，CPU 峰值 44%。修复后，第 3 段兜底 0 次，第 4 段 2 次。
- OCR 平均置信度 0.27–0.57，偏低，中文界面的小字识别质量一般。OCR 只适合作兜底，不能作主要来源。
- 第一次截图曾经卡住，导致之后的 OCR 全部挂起。已加 10 秒超时，第 4 段触发过 1 次。正式版也要有超时。

### 3.3 Chrome

- AppleScript 取网址：473 次，100% 成功，中位 31–37 ms。
- 正文：辅助功能能读到。滚出视野的部分能按坐标排除。
- 大页面读取较慢：中位 161 ms，21% 的读取到了 400 ms 上限被截断。正式版要为 Chrome 单独限时，或只读焦点标签页的可视区域。
- 历史库：没有完全磁盘访问权限就读不到。

### 3.4 数据量与模型用量

| 段 | 场景 | 新增字数 / 小时 | 其中中文 | 估算 token / 小时 | 每 15 分钟 |
| --- | --- | --- | --- | --- | --- |
| 3 | AI 对话为主（Codex） | 51,824 | 31,957 | 36,924 | 9,231 |
| 4 | 看网页为主（Chrome 占三分之二） | 254,530 | 99,861 | 138,528 | 34,632 |

token 粗估方式：中文 1 字≈1 token，其他 4 字符≈1 token。

两段差了约 4 倍。看网页时，每滚动一次就是整屏新文字。

这些都是**偏高的上限**：

- 「新增」只和同一窗口的上一次采样比较。内容离开再回来会重复计入，正式版按全天去重会少很多。
- 没有扣掉界面上的固定文字（菜单、按钮）。
- 每段只有 10–30 分钟。

按这个上限，一天 10 小时的整理输入在 37 万到 140 万 token 之间。整理模型应该选便宜的；发送前要按全天去重，必要时先在本机压缩。

## 4. 未决项

| 项 | 情况 | 建议 |
| --- | --- | --- |
| 屏幕窗口与辅助功能窗口匹配率 | 第 1 段 100%，第 2 段 91%，第 3 段 78%，第 4 段 99% | 不匹配集中在多窗口并排时。M4 查清原因：私有 API `_AXUIElementGetWindow` 失败，还是坐标匹配失败。匹配不上的窗口记为「不可读」，不能悄悄丢掉 |
| 未测的 App | 微信、飞书、Slack、邮件、Office/WPS、Xcode | 正式版的「读取状态」统计会覆盖这些 App |
| 全天用量 | 有效数据约 40 分钟，两段相差 4 倍 | M5 白天整理上线后用真实 token 计数校准 |
| Chrome 大页面读取慢 | 21% 到 400 ms 上限 | M4 为 Chrome 单独限时，或只读可视区域 |
