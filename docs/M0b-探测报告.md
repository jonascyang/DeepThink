# M0b 探测报告

日期：2026-10-31。探测程序：`tools/M0bProbe`，最终版本 build 20261031135015。

报告只含统计数字。探测程序不保存屏幕文字、窗口标题或网址。

## 1. 结论

| 问题（PRD §13） | 结论 |
| --- | --- |
| 自签证书下授权是否保留？ | **保留。** 用固定证书「ThinkMyDay Local Signing」签名，指定要求（DR）是 identifier 加证书 leaf。前后重新构建并安装约 10 次，辅助功能和屏幕录制都不用重新授权。签名第一次使用钥匙串时，要点一次「始终允许」。 |
| 常用 App 能用辅助功能读到多少文字？ | **测到的 App 都能读到。** 修正可见性规则后，Claude、ChatGPT（Codex）、Chrome、终端的「不可读」比例都是 0%。和 OCR 对照，AX 可见字数 ÷ OCR 字数为 1.2–1.7。 |
| Chrome 正文能否通过辅助功能读到？ | **能。** 不需要 `AXEnhancedUserInterface`（返回 -25208，不支持），正文本来就能读到。滚出视野的内容可以按坐标正确排除。 |
| Electron 是否需要 `AXManualAccessibility`？ | 设置会成功（返回 0），但测到的 Electron App 在设置前就能读到文字，设置前后字数相同。保留这一步，没有副作用。 |
| 多窗口、多屏 | 97–100% 的采样同时有 2 个以上窗口，分布在 2 块屏幕上。91–98% 能识别出焦点窗口。屏幕窗口和辅助功能窗口的匹配率为 78–100%（见 §4 未决项）。 |
| OCR | 能用，但正常情况下基本用不上。识别一个窗口：截图约 40–90 ms，识别 0.4–0.6 s，最慢约 2.2 s。平均置信度只有 0.5–0.56。 |
| 资源占用 | 修复后 CPU 平均 0.5–0.8%，p95 1.5%，内存约 53–55 MB。单次采样（读所有可见窗口）中位 92–124 ms。 |
| 白天整理的用量 | 每小时约 3.7 万 token，按 15 分钟一次，每次约 9 千 token。这是**上限估计**，见 §3.4。 |
| Chrome 历史库 | **读不到。** 系统拒绝访问 `~/Library/Application Support/Google/Chrome`，提示 “you don’t have permission to view it”。macOS 保护其他 App 的数据，需要「完全磁盘访问权限」。 |

## 2. 测试情况

- 机器：Jonas 的 Mac，macOS 27（Darwin 27.0.0），两块屏幕。
- 数据分三段：
  1. 2026-10-30 19:57–22:06，2.15 小时，1,748 次采样。
  2. 2026-10-31 12:11–13:19，1.14 小时，834 次采样。
  3. 2026-10-31 13:50–14:00，最终版本，115 次采样。
- 第 1、2 段用的版本有可见性 bug（§3.1）。这两段的授权、多窗口、Chrome 网址、OCR 耗时、资源数据有效，可读率和字数无效。可读率、字数、token 用第 3 段。
- 覆盖的 App：
  - 主要是 ChatGPT（Codex，`com.openai.codex`）、Claude（`com.anthropic.claudefordesktop`）、Chrome。
  - 少量的有终端、系统设置、Cursor 类编辑器（`com.anysphere.sand`）、Quicall、Clash Verge。
  - **没有测到**微信、飞书、Slack、邮件、Office/WPS、Xcode 等。

## 3. 发现

### 3.1 Chromium 的可见性规则（对 M4 记录层最重要）

探测程序判断「哪些文字在屏幕上可见」，前后修了四次。每一处都是 Chromium 和 Electron 的特有行为，正式的记录层必须照着处理：

1. **`AXVisibleCharacterRange` 不可靠。** 普通文字（AXStaticText）几乎都报一个很短的范围，导致几千字被算成 1 字。现在只在可编辑控件（AXTextArea、AXTextField、AXComboBox）上用它裁剪长文本，其他元素按坐标判断。
2. **按钮、链接、标题的「标题」就是子元素的文字。** 两样都计入会重复计数。现在只在叶子元素上读标题。
3. **滚出视野的文字会被压成 1 pt 高的细条，贴在滚动区域边上，不会给出视野外的坐标。** Codex 里有 3,000 多字是这种情况。现在宽或高小于 2 pt 的元素算不可见。另外也按 AXScrollArea 和 AXWebArea 的边界裁剪。
4. **单行标签里藏着完整文本，屏幕上只显示一行加省略号。** 比如一个按钮带 612 字的预览，但只有一行宽。现在按框的大小估算容量上限：每字至少 6 pt，每行至少 14 pt。

修正后，两次 OCR 对照的 AX÷OCR 为 1.16 和 1.73。AX 略多是正常的，因为 OCR 会漏掉小字、灰字和空格。

> 产品取舍：第 4 条只用于估算「屏幕上看得到多少」。记录层是否保留被省略号截掉的全文，要另外决定。保留的话内容更完整，但要发给模型的 token 更多。

### 3.2 OCR 兜底

- 修复前，可见性 bug 让 OCR 兜底触发了 416 次，CPU 峰值 44%。修复后，兜底 0 次，CPU 平均 0.5%。
- OCR 平均置信度 0.5–0.56，偏低，中文界面的小字识别质量一般。OCR 只适合作兜底，不能作主要来源。
- 第一次截图曾经卡住，导致之后的 OCR 全部挂起。已加 10 秒超时。正式版也要有超时。

### 3.3 Chrome

- AppleScript 取网址：412 次，100% 成功，中位 31–37 ms。
- 正文：辅助功能能读到。滚出视野的部分能按坐标排除（每次采样约 150 个元素被排除）。
- 历史库：没有完全磁盘访问权限就读不到。

### 3.4 数据量与模型用量

第 3 段（Codex 在前台、78% 时间是焦点，Claude 在旁边可见）：

| 项 | 每小时 | 每 15 分钟 |
| --- | --- | --- |
| 新增字数 | 51,824 | 12,956 |
| 其中中文 | 31,957 | 7,989 |
| 估算 token（中文 1 字≈1 token，其他 4 字符≈1 token） | 36,924 | 9,231 |

这是**偏高的上限**：

- 「新增」只和同一窗口的上一次采样比较。内容离开再回来会重复计入，正式版按全天去重会少很多。
- 只测了 10 分钟，而且是 AI 对话这类文字密集的使用场景。
- 没有扣掉界面上的固定文字（菜单、按钮）。

按这个上限，一天 10 小时的整理输入约 37 万 token。

## 4. 未决项

| 项 | 情况 | 建议 |
| --- | --- | --- |
| 屏幕窗口与辅助功能窗口匹配率 | 第 1 段 100%，第 2 段 91%，第 3 段 78% | M4 查清原因：私有 API `_AXUIElementGetWindow` 失败，还是坐标匹配失败。匹配不上的窗口记为「不可读」，不能悄悄丢掉 |
| 未测的 App | 微信、飞书、Slack、邮件、Office/WPS、Xcode | 正式版的「读取状态」统计会覆盖这些 App；或者探测程序再跑一天，期间用这些 App |

| 被省略号截掉的全文是否记录 | 见 §3.1 | 产品决定 |
